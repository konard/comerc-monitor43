# План сокращения undefined BDD-шагов

Документ фиксирует рабочий план по разбору `pending` и `undefined` шагов в `features/**`.

Цель - сократить шум в BDD-слое без разрушения ownership эпиков и без перехода к глобальной регистрации всех шагов. Недостающие шаги необходимо реализовать, согласно соглашениям. Итог выполнения всей задачи - в файле out.txt должно быть 0 записей! 

ЗАДАЧУ НЕОБХОДИМО ВЫПОЛНИТЬ ПОЛНОСТЬЮ БЕЗ УТОЧНЯЮЩИХ ВОПРОСОВ. ВЫПОЛНИ СТОЛЬКО ИТЕРАЦИЙ, СКОЛЬКО ПОТРЕБУЕТСЯ ДЛЯ ДОСТИЖЕНИЯ ЦЕЛИ.

## Текущее состояние

Источник первичного анализа:

```bash
task bdd-pending > out.txt
task bdd-inventory > /tmp/bdd-inventory.md
```

`task bdd-pending` запускает полный BDD-прогон и занимает около 12 минут.
`task bdd-inventory` работает по уже сохраненному `out.txt` и нужен для быстрых итераций планирования.

Сводка по текущему `out.txt`:

| Epic | Total | Undefined | Pending |
|---|---:|---:|---:|
| `01_monitoring` | 611 | 611 | 0 |
| `02_alerting` | 95 | 43 | 52 |
| `03_dashboard` | 790 | 741 | 49 |
| `04_billing` | 640 | 640 | 0 |
| `05_security` | 33 | 2 | 31 |
| `06_reporting` | 270 | 270 | 0 |
| `07_integrations` | 458 | 458 | 0 |
| `08_maintenance` | 237 | 225 | 12 |
| `09_scheduler` | 216 | 216 | 0 |
| `10_check_worker` | 247 | 247 | 0 |

Главный вывод: проблема не сводится к отсутствию одного общего регистратора.
Часть шагов не видна из-за per-epic регистрации, часть отличается формулировкой от уже существующих regex, а часть сценариев пока шире текущей автоматизации.

## Архитектурное решение

`registerEpicSteps` остается per-epic.

Не вводим модель `RegisterAllSteps`, потому что она размывает ownership и создает риски:

- конфликты и ambiguous regex между эпиками;
- выполнение чужих `ctx.Before` хуков;
- неявная зависимость от полей `ScenarioState`;
- сложность понять, какой epic владеет шагом.

Общие шаги допустимы, но подключаются явно в нужном case:

```go
case len(epicName) >= 2 && epicName[:2] == "04":
    RegisterCommonAuthSteps(ctx, state)
    RegisterCommonResponseSteps(ctx, state)
    RegisterCommonAuditSteps(ctx, stack, state)
    RegisterBillingSteps(ctx, stack, state)
```

Правило: common-регистратор содержит только сквозной язык, который реально используется несколькими эпиками.
Доменные шаги остаются в `steps_NN_*.go`.

## Классификация шагов

Каждый уникальный шаг из inventory нужно отнести к одной категории.

| Категория | Значение | Действие |
|---|---|---|
| `alias` | Реализация уже есть, но текст в `.feature` отличается | Нормализовать `.feature` или добавить узкий alias |
| `common` | Шаг нужен нескольким эпикам и не содержит доменной логики | Вынести в `steps_common.go` или новый `steps_common_*.go` |
| `domain` | Шаг принадлежит одному epic | Реализовать в соответствующем `steps_NN_*.go` |
| `pending` | Шаг найден, но осознанно возвращает `godog.ErrPending` | Оставить с TODO или реализовать в рамках epic |
| `backlog` | Сценарий продуктово описан, но автоматизация пока не нужна | Явно пометить как pending или вынести из исполняемого набора |
| `rewrite` | Шаг слишком UI/технический или плохо выражает бизнес-поведение | Переписать сценарий |

## Порядок работы

### 1. Поддерживать быстрый inventory

Не запускать полный BDD-прогон на каждую гипотезу.
Рабочая петля:

```bash
task bdd-pending > out.txt     # редко, когда нужен свежий снимок
task bdd-inventory > /tmp/bdd-inventory.md
```

Для анализа брать top repeated steps и детали по одному epic.

### 2. Разбирать один epic за итерацию

Приоритет по текущему объему:

1. `03_dashboard` - 741 undefined, 49 pending.
2. `04_billing` - 640 undefined.
3. `01_monitoring` - 611 undefined.
4. `07_integrations` - 458 undefined.
5. `10_check_worker` - 247 undefined.
6. `08_maintenance` - 225 undefined, 12 pending.
7. `09_scheduler` - 216 undefined.
8. `06_reporting` - 270 undefined.
9. `02_alerting` - 43 undefined, 52 pending.
10. `05_security` - 2 undefined, 31 pending.

Порядок можно менять, если текущая разработка касается конкретного epic.

### 3. Сначала закрывать повторяющиеся common-кандидаты

Текущие заметные кандидаты:

| Шаг | Повторы | Решение |
|---|---:|---|
| `And ответ содержит структуру:` | 64 | `RegisterCommonResponseSteps` |
| `And audit log содержит:` | 42 | `RegisterCommonAuditSteps` |
| `And создается запись audit log:` | 13 | `RegisterCommonAuditSteps` или нормализация текста |
| `Then система возвращает ошибку "..."` | много вариантов | `RegisterCommonErrorSteps` |
| `And действие в аудит лог записано как "..."` | много вариантов | `RegisterCommonAuditSteps` |

Перед выносом common-шагов проверить, что реализация не привязана к таблицам конкретного сервиса.
Если шагу нужен доменный репозиторий или клиент, он не common.

### 4. Затем нормализовать alias

Типовые несовпадения:

| Feature text | Existing/desired canonical text |
|---|---|
| `монитор должен быть создан успешно` | `монитор создан успешно` |
| `монитор должен иметь статус "..."` | `монитор имеет статус "..."` |
| `пользователь имеет монитор с именем "..."` | `пользователь имеет монитор "..."` |
| `ответ содержит структуру:` | единый common-шаг |

Предпочтение: исправлять `.feature` на каноническую фразу, если это не ухудшает бизнес-язык.
Alias добавлять только когда обе формулировки действительно устойчиво используются.

### 5. Доменные шаги реализовывать пачками

Для каждого epic:

1. Открыть соответствующий раздел в `/tmp/bdd-inventory.md`.
2. Выделить top 10-20 шагов по повторам.
3. Разметить категории `alias/common/domain/pending/backlog/rewrite`.
4. Реализовать только одну небольшую группу за раз.
5. Запустить точечный BDD-пакет:

```bash
go test -timeout 20m -p 1 -v -tags bdd ./features/04_billing
```

Полный прогон `./features/...` запускать после завершения крупной пачки.

## Definition of Done для итерации

Итерация считается завершенной, когда:

- обновлен inventory по затронутому epic;
- новые common-шаги подключены явно только в нужных epic;
- нет новых ambiguous/duplicate step definitions;
- количество `undefined` по epic уменьшилось или часть шагов осознанно переведена в `pending/backlog`;
- точечный BDD-прогон по epic выполнен или явно указан блокер.

## Не делать

- Не заменять `registerEpicSteps` на глобальный `RegisterAllSteps`.
- Не переносить доменную логику в `steps_common.go`.
- Не добавлять широкие regex вида `^.*$` или слишком общие catch-all шаги.
- Не скрывать реальные пробелы через `godog.ErrPending` без TODO и причины.
- Не запускать полный 12-минутный BDD-прогон после каждой мелкой правки.
