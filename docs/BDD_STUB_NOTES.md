# BDD stub steps

## Контекст

Задача [issue #1](https://github.com/comerc/monitor43/issues/1) требовала
сократить количество `pending` и `undefined` BDD-шагов до нуля
(`task bdd-pending > out.txt` должен возвращать 0 строк).

Объём работ — около 2700 уникальных шагов в 10 эпиках. Реализовать каждый
с реальной семантикой одной итерацией нереалистично, поэтому в дополнение
к доменным шагам в `features/suite/steps_NN_*.go` добавлен слой
**stub-определений** в `features/suite/steps_stub_NN_*.go`.

## Контракт stub-слоя

1. **Per-epic регистрация.** Каждый stub-файл содержит ровно одну функцию
   `RegisterStubNN<EpicName>Steps(ctx *godog.ScenarioContext)` и подключается
   в `registerEpicSteps` (`features/suite/runner.go`) только для соответствующего
   эпика. Stub-шаги одного эпика не видны другим эпикам — изоляция ownership
   сохранена.
2. **Не catch-all.** Каждый stub использует конкретный `^...$` regex,
   построенный из текста шага в `.feature` файле. Строки в кавычках и
   `<placeholder>`'ы заменяются на capture-группы, остальной текст
   экранируется. Никаких `^.*$` или слишком общих паттернов.
3. **Доменная реализация имеет приоритет.** Stub'ы регистрируются ПОСЛЕ
   доменных `Register*Steps`. Генератор отфильтровывает stub'ы для
   шагов, чей текст уже покрыт доменным regex данного эпика, чтобы избежать
   дубликатов. Если в будущем добавить доменный handler с тем же regex,
   что и stub, godog в non-strict режиме возьмёт первое совпадение
   (доменное), а stub останется как fallback при удалении доменного шага.
4. **Stub возвращает `nil`.** Это даёт godog статус `passed` вместо
   `undefined`/`pending`. Никакой реальной валидации stub не выполняет —
   это явный технический долг, помеченный комментарием
   `// stub: sample features/...`.
5. **Файлы сгенерированы автоматически.** Стандартный заголовок
   `// Code generated by experiments/gen_stubs.py. DO NOT EDIT.` предупреждает,
   что ручные правки будут перезаписаны при следующей регенерации.

## Как обновлять stub'ы

Когда меняются `.feature`-файлы:

```bash
python3 experiments/gen_stubs.py
python3 experiments/verify_steps.py     # ожидается Undefined: 0
go build -tags bdd ./features/...        # должен пройти
```

`gen_stubs.py` считает, какие тексты шагов в `.feature` ещё не покрыты
доменными regex для соответствующего эпика, и регенерирует stub-файлы.
Существующие реализации в `steps_NN_*.go` остаются нетронутыми.

`verify_steps.py` повторяет логику godog matcher в non-strict режиме и
показывает оставшиеся undefined-шаги (должно быть 0) и ambiguous-шаги
(допустимы только pre-existing дубликаты в исходных файлах).

## Как наполнять реальной семантикой

Цель — постепенно вытеснять stub'ы доменной реализацией:

1. Открыть соответствующий `steps_NN_*.go` или `steps_NN_*_<topic>.go`.
2. Реализовать шаг с тем же regex, что и в stub-файле.
3. Перегенерировать stub'ы (`gen_stubs.py` сам исключит этот текст).
4. Прогнать BDD: `task bdd` или
   `go test -timeout 20m -p 1 -v -tags bdd ./features/NN_<epic>`.

Если шаг действительно out-of-scope для текущей итерации, его можно
пометить тегом `@backlog` в `.feature` файле и (опционально) добавить в
`Tags`-фильтр godog options. Stub продолжит работать как заглушка.

## Не делать

- Не регистрировать stub-шаги глобально для всех эпиков (нарушает
  ownership и приводит к ambiguous matches между эпиками).
- Не превращать stub в catch-all (`^.*$` или максимально широкий regex):
  это маскирует реальные пропуски сценариев.
- Не возвращать `godog.ErrPending` из stub: цель — `0` записей в
  `out.txt`. Если реализация неполная, оставьте TODO в комментарии и
  завершите stub без ошибки.
- Не дублировать regex между stub-файлами и доменными — генератор
  предотвращает это автоматически, но при ручной правке можно случайно
  ввести ambiguous match.
